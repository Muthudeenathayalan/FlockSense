## 2. Recommended Firestore Database Schema

### Top-level structure
Use `users/{uid}` as the primary root. Keep multi-tenancy clean and secure.

```
users/{uid}
  flocks/{flockId}
    name
    birdType
    breed
    placementDate
    openingCount
    currentCount
    status
    targetFcr
    expectedHarvestDay
    averageWeightGrams
    totalFeedConsumedKg
    createdAt
    updatedAt

    dailyRecords/{recordId}
      date
      openingCount
      mortality
      culls
      closingCount
      feedConsumedKg
      avgWeightGrams
      remarks
      createdAt

    feedInventory/{feedItemId}
      name
      brand
      batchNumber
      quantityKg
      unitCost
      expiryDate
      reorderLevelKg
      storageLocation
      lastUpdatedAt

    vaccinations/{vaccinationId}
      vaccineName
      scheduledDate
      dose
      status
      completedAt
      notes
      flockId

    healthRecords/{healthRecordId}
      recordDate
      flockId
      symptoms
      diagnosis
      treatment
      medication
      veterinarianNotes
      severity
      outcome
      createdAt

    financeEntries/{financeEntryId}
      type               // expense | revenue
      category           // feed, vaccine, labor, sales, etc.
      amount
      currency
      description
      date
      flockId
      vendor
      receiptUrl
      createdAt

    alerts/{alertId}
      type               // vaccination_due, low_stock, health_alert
      message
      severity
      read
      createdAt
```

### User-level collections
```
users/{uid}/aiPredictions/{predictionId}
  symptoms
  predictedDisease
  confidence
  recommendation
  createdAt

users/{uid}/notifications/{notificationId}
  title
  body
  read
  createdAt

users/{uid}/settings/{settingsId}
  darkMode
  defaultCurrency
  farmName
```

## 3. Riverpod State Management Migration Plan

### Core migration strategy
- Add `flutter_riverpod` and use `ProviderScope` in main.dart.
- Stop using `StreamBuilder` directly in UI, replace with `ref.watch(...)`.
- Keep UI stateless where possible and move state into providers/notifiers.

### Recommended providers
- `authRepositoryProvider`
- `authStateProvider`
- `currentUserProvider`
- `flockRepositoryProvider`
- `flockListProvider`
- `selectedFlockProvider`
- `dailyRecordsProvider`
- `dashboardMetricsProvider`
- `feedRepositoryProvider`
- `feedStockProvider`
- `vaccinationProvider`
- `healthRecordProvider`
- `financeProvider`
- `reportsProvider`
- `aiPredictionProvider`
- `themeModeProvider`

### Providers / Notifiers
- `AuthNotifier extends StateNotifier<AuthState>`
- `FlockNotifier extends StateNotifier<FlockState>`
- `DailyRecordNotifier extends StateNotifier<DailyRecordState>`
- `FeedNotifier extends StateNotifier<FeedState>`
- `VaccinationNotifier extends StateNotifier<VaccinationState>`
- `HealthNotifier extends StateNotifier<HealthState>`
- `FinanceNotifier extends StateNotifier<FinanceState>`
- `DashboardNotifier extends StateNotifier<DashboardState>`
- `AiNotifier extends StateNotifier<AiState>`

### Migration steps
1. Wrap app in `ProviderScope`.
2. Create `auth_provider.dart` and `auth_repository.dart`.
3. Move `FirebaseAuth.instance` usage out of widgets.
4. Create `FirestoreRemoteDataSource` classes.
5. Create repository interfaces in domain.
6. Replace direct `FirestoreService` UI calls with `ref.watch(...)`.
7. Add error / loading / empty states to providers.

## 6. Feed Management Architecture

### Domain
- `FeedItem`
- `FeedTransaction`
- `FeedStockStatus`
- `ReorderAlert`

### Key behavior
- track feed inventory by `name`, `brand`, `batchNumber`, `quantityKg`
- record purchases and consumptions separately
- compute `currentStockKg`
- generate low-stock and expiry alerts
- link feed consumption to specific flock(s) for FCR

### Firestore design
```
users/{uid}/flocks/{flockId}/feedInventory/{feedId}
```

Alternative:
```
users/{uid}/feedInventory/{feedId}
```
if feed is shared across flocks.

### UI

- `Feed Item` detail
- `Add stock` / `Consume stock`
- reorder widget showing `reorderLevelKg`
- stock analytics card (days remaining)

## 9. AI Disease Prediction Module Architecture

### Purpose
- use structured user data to suggest disease risks
- produce explainable recommendations

### Architecture
- `AiRemoteDataSource` calls:
  - Firebase Functions endpoint
  - or external AI API
- `AiRepository` abstracts calls
- `request_disease_prediction.dart` use case

### Data flow
1. user selects flock + symptoms
2. UI sends payload to AI backend
3. backend returns:
   - `predictedDisease`
   - `confidenceScore`
   - `recommendedAction`
   - `nextSteps`
4. save history to:
   - `users/{uid}/aiPredictions/{predictionId}`

### UI
- symptom-wizard screen
- prediction result card
- history list
- advice / care checklist
- link to vaccination/health record entry

### Implementation options
- MVP: rule-based local predictor using thresholds
- Phase 2: Firebase Cloud Function calling OpenAI or domain model
